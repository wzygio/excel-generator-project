3. 理想效果：用户可以再输入框中输入需求，Agent根据用户需求完成相应任务。

这样当用户想要修改分析流程时，只需要用自然语言修改spec文件即可，而不是让程序员修改代码。
4. Agent核心：此前我将Agent核心交给了LLM，这是因为我此前不知道Codex还有CLI。能够将Agent核心更换为Codex，也就是说：Codex通过UI接收用户需求，然后调用每个模块的执行任务。

后者的优势在于速度和成本，但是劣势在于过于固化，不懂代码的人无法对其进行修改。

【Task5】
1. 请问当运行“日报生成→数据分析→报表下载”这条链路时，规则是如何向下传递的？针对每个模块，是否有“用户自定义spec→skill→代码”这样的传递机制？
2. 我是否有可能在不借助Codex的情况下，直接修改规则即可修改项目？比如我想加上Task3的几条规则，直接在spec文件中维护即可。

【illustration】
1. Codex定位：抱歉，您理解错了，我说的不借助Codex是指不借助Codex Desktop来修改项目代码。但是整个Agent的核心依旧是Codex。
2. 执行机制：“日报生成 > 数据分析 > 报表下载”这是任务链，是执行机制，您也可以继续使用“代码内嵌调用链”的模式，这样速度更快。
3. 迭代机制：但我想讨论的是需求信息传递链，是迭代机制，简而言之，我们要实现用户可以在一定程度上微调项目，比如通过自然语言修改规则。
4. 项目缺陷：当前情况下，“代码内嵌调用链”是写死的，skill目前也是写死的，不能够根据用户的要求来微调规则。如果想要改动，哪怕只是微调，都只能够根据身为开发者的我来进行修改。这样会导致项目不够灵活，无法达成我们“用户自定义维护项目”的终极目标。
5. 维护机制：我的想法是，就像很多智能体设计平台能够提供system prompt设计一样，我们能否暴露一个spec接口能够让用户修改，然后Codex可以分通过分析用户对于spec的修改来调试底层skill或代码，从而满足用户要求。
6. 修改界限：关键在于允许用户修改的界限，它不能够重构整个项目，而只能够增添或减少一些规则。我认为这样Codex还是可以做到的。
